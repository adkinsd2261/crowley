# V4.3.3R — Recovery Foundation and Database Adoption Plan

**Status:** Approved by Mr. Go on 2026-07-28 for ticket minting — only R1 activates initially
**Baseline:** `main` at `ab04924189cde80cb80b341fcbf3256b236497c3`
**Depends on:** V4.3.2 Spark Corpus Expansion lock
**Supersedes:** V4.3.3 Legacy Memory Final Drain #491–#495 (historical rows absent from the reset database; see supersession notice)
**North star:** [V5_LIFE_READY_COGNITIVE_OS_PLAN.md](./V5_LIFE_READY_COGNITIVE_OS_PLAN.md)

---

## 1. Goal

Make Crowley's durable state evolvable and recoverable before chat sessions,
Spaces, personal operations, Forge execution, or external connectors add more
consequential state.

V4.3.3R must:

- preserve and classify the current database before changing it;
- create an ordered, recorded migration path for empty and existing databases;
- stop reporting healthy startup after required initialization fails;
- establish SQLite integrity and foreign-key policy;
- produce verified, encrypted recovery bundles without storing the only key
  beside the backup;
- prove clean bootstrap, existing-database adoption, isolated restore, and
  failure behavior;
- define the compatibility role of legacy memory without using historical row
  counts as current truth.

This release does not wipe, drain, or replace the current database.

---

## 2. Repository context

### Committed baseline

- `crowley_core.connect_db()` enables WAL and busy timeout but not foreign keys.
- `crowley.setup_db()` creates the legacy schema in one broad block.
- memory, audit, conflict, observability, and Spark subsystems create or amend
  schema through separate setup functions.
- required memory and Spark initialization errors can be swallowed.
- only Spark and Spark-link tables declare foreign keys.
- no `schema_migrations` table or ordered migration runner exists.
- isolated tests call `setup_db()` against temporary databases, providing a
  useful compatibility harness but not a migration/restore acceptance suite.
- V4.3.3 #491–#495 assumes historical database counts and a remaining corpus
  drain. Those counts are not authoritative for the current workspace database.

### Current working tree

Uncommitted recovery work already proposes:

- SQLite online snapshot;
- manifest with checksum, quick check, selected table counts, Git and machine
  metadata;
- restic encryption and off-device repository support;
- DPAPI-sealed local credentials on Windows;
- isolated restore and hash/integrity verification;
- scheduled backup/check tasks;
- focused backup tests and operator documentation.

This work is valuable input. It must be reviewed as existing user work, not
recreated, overwritten, or treated as shipped. V4.3.3R planning does not assume
that its code or external R2/restic configuration has been verified.

### Runtime recovery status

On 2026-07-28, the broken Python 3.11-backed `venv` was preserved as
`venv.broken-20260728`, Python 3.12.10 was installed from a signature-verified
Python Software Foundation installer, and a clean `venv` was created with the
core dependencies and `sqlite-vec`. Focused recovery/runtime and agent-sync
tests passed. R1 still owns turning that machine repair into a reproducible,
repository-supported preflight and preservation contract.

## 3. Non-goals

- Deleting or bulk-archiving current database rows.
- Replaying historical lock artifacts as live events.
- Completing the old V4.3.3 corpus-count targets.
- Creating the full V5 receipt/source/event model.
- Creating Spaces, sessions, personal operations, agent runs, or durable jobs.
- Rebuilding all legacy tables merely to add foreign keys.
- Removing legacy public functions, API shapes, or `crowley.py` compatibility.
- Migrating all domain logic into a new package tree.
- Implementing MCP, connectors, voice, or autonomous shell execution.
- Claiming a backup is recoverable based only on upload success.

## 4. Required decisions

The following decisions are proposed for approval with this plan:

1. **Adoption, not reset.** Existing databases are inspected and adopted through
   a recorded baseline migration; empty databases run the full creation path.
2. **Hybrid state plus migration ledger.** V4.3.3R does not introduce full
   event sourcing.
3. **Required/optional initialization.** Core schema, audit, observability, and
   Sparks are required. Optional embedding/vector acceleration may be degraded.
4. **Progressive foreign keys.** Enable enforcement for every connection after
   an orphan preflight. New schemas require constraints. Legacy table rebuilds
   occur only when a focused migration justifies them.
5. **No canonical Space yet.** Preserve the default Crowley project and record
   seed provenance; defer Space identity to the Spaces decision.
6. **Legacy memory remains compatibility state.** Do not call all
   `memory_items` immutable receipts. New cognitive paths remain Spark-first,
   and V4.4 will make legacy retrieval an explicit cold-start fallback.
7. **Restore verification is application-aware.** Hash and SQLite integrity are
   necessary but insufficient; restored state must pass migrations, startup,
   required subsystem health, and bounded smoke checks.

## 5. Migration contract

### Migration record

The migration ledger should minimally record:

- ordered migration ID;
- name;
- checksum;
- applied timestamp;
- application/repository version where available;
- execution duration;
- adoption or normal-apply mode;
- success only after transaction commit.

Failed migrations are reported through startup diagnostics and logs, not
recorded as successfully applied.

### Empty-database path

An empty path must:

1. create the migration ledger;
2. apply the ordered baseline schema;
3. initialize all required subsystems;
4. seed only documented default state;
5. run integrity and required health checks;
6. produce a deterministic schema fingerprint.

### Existing-database adoption

An existing database must:

1. be snapshotted before adoption;
2. pass `integrity_check`;
3. inventory tables, columns, indexes, triggers, and foreign keys;
4. compare required schema signatures;
5. audit orphaned references relevant to current declared foreign keys;
6. reject unknown incompatible layouts;
7. record the audited baseline adoption;
8. apply later migrations normally;
9. preserve all rows unless a separately approved migration changes them.

Adoption must not claim that historical migrations ran when they did not.
Migration metadata should explicitly identify baseline adoption.

### Transaction and locking policy

- One migration owner at startup.
- Ordered application under a bounded write lock.
- No healthy app service before required migrations complete.
- Each migration is repeat-safe by recorded identity and checksum.
- Checksum mismatch for an already-applied migration fails loudly.
- Failure leaves the last committed schema usable where SQLite semantics allow.
- Recovery instructions identify the pre-migration snapshot.

## 6. Initialization and health contract

Replace broad setup exception suppression with an explicit registry:

| Subsystem | V4.3.3R status | Failure behavior |
|---|---|---|
| Core legacy compatibility schema | Required | Startup unhealthy/fails |
| Migration ledger/runner | Required | Startup unhealthy/fails |
| Write audit | Required | Startup unhealthy/fails |
| Observability/session-state support | Required | Startup unhealthy/fails |
| Sparks, links, patterns | Required | Startup unhealthy/fails |
| Memory compatibility columns | Required | Startup unhealthy/fails |
| Embedding provider/vector extension | Optional | Degraded with reason |
| External model providers | Optional | Degraded with reason |
| External tunnels/connectors | Optional | Degraded with reason |

Health output should expose:

- database path identity without secrets;
- schema/migration version;
- integrity status from the most recent bounded check;
- required subsystem status;
- optional degradation reasons;
- backup freshness and last verified restore drill when available;
- startup failure identity suitable for operator diagnosis.

No exception text containing credentials or sensitive values may be exposed.

## 7. SQLite integrity and foreign-key policy

1. Every normal connection enables:
   - `foreign_keys=ON`;
   - existing WAL and busy timeout settings.
2. Connection tests assert the pragma is active.
3. Adoption runs `foreign_key_check` and targeted orphan reports before the
   enforcement change is accepted.
4. Existing bad references block adoption or require an explicit repair plan;
   they are not silently deleted.
5. Every new durable V5 table declares relevant foreign keys, indexes, uniqueness
   rules, and delete/update behavior.
6. Legacy tables gain constraints only through focused table-rebuild
   migrations with row-preservation and rollback tests.
7. Integrity checks are bounded and scheduled appropriately; startup must not
   perform an unbounded full scan on every request.

## 8. Backup bundle and key contract

The current recovery implementation should be reviewed and adapted rather than
discarded.

### Bundle scope

The manifest must explicitly classify:

- SQLite online snapshot;
- schema/migration version and schema fingerprint;
- repository revision and dirty-state flag;
- managed artifact directories included;
- non-secret operating configuration included;
- required configuration intentionally excluded;
- secrets and credentials intentionally excluded;
- embedding/index rebuild metadata;
- checksums for every included durable artifact;
- backup-tool and manifest format versions.

The plan must decide the durable status of `.crowley/processed`, inbox state,
brain configuration, future artifact roots, connector configuration, and
schedule definitions. “Selected useful files” is not a stable long-term
contract.

### Keys

- Backup encryption keys are not stored in the ordinary database or backup.
- Local sealed credentials are convenience, not replacement-machine recovery.
- A documented password-manager/offline recovery record is required.
- Missing-key behavior is tested and fails clearly.
- Key rotation is deferred unless needed to make the selected backup mechanism
  safe; the recovery record must document how repository password changes are
  handled.

### Verification

A verified drill must:

1. restore into a new isolated path;
2. validate manifest and artifact checksums;
3. run SQLite `integrity_check`;
4. compare required table/schema signatures;
5. run migrations against the restored copy;
6. start required services against the restored copy without touching live
   state;
7. run bounded health and cognitive/ticket smoke checks;
8. record a drill report;
9. leave the live database unchanged.

An off-device provider is operational configuration. Unit and local integration
tests must also support a local restic repository or equivalent isolated
backend.

## 9. Authoritative seed and incident policy

### Incident

Add a durable repository incident/ADR recording:

- what is known and unknown about the historical database loss;
- which Git artifacts survived;
- why historical corpus reports are not current row truth;
- how the present database was obtained, when known;
- which recovery controls V4.3.3R introduces.

Do not insert a fabricated “database loss event” into the current database
unless a later event model records it explicitly as a repository-sourced
historical incident.

### Seed manifest

Document every empty-database seed:

- stable identity;
- target table/domain;
- authoritative source file or code constant;
- why it is required;
- whether users may modify it;
- idempotency key or uniqueness rule.

The V4.3.3R seed remains the compatibility Crowley project, not a prematurely
defined Space.

## 10. Proposed execution slices

These are planning slices, not minted tickets.

### R1 — Runtime preflight and state preservation

**Goal:** Establish an executable environment and preserve current durable
state before schema work.

**Scope:**

- reproducible Python setup/install verification;
- database metadata/integrity inspection with no content export;
- pre-change online snapshot;
- recovery-work diff review;
- provenance status report.

**Done when:**

- clean environment instructions create a working interpreter;
- focused baseline tests run;
- current database is preserved and classified;
- no live rows are changed.

### R2 — Schema inventory and migration RFC lock

**Goal:** Make all current schema ownership explicit and lock the migration
contract before implementing it.

**Scope:**

- generated or reviewed schema inventory;
- required/optional subsystem list;
- migration record and checksum semantics;
- empty/adoption behavior;
- transaction, concurrency, and failure policy;
- compatibility map for tests, APIs, tools, and setup helpers.

**Done when:**

- inventory covers every committed schema creator and runtime column addition;
- ambiguities are resolved in the plan;
- no migration code lands before this contract is reviewed.

### R3 — Ordered migration runner and baseline adoption

**Goal:** Replace implicit schema evolution with recorded migrations while
preserving existing databases.

**Scope:**

- migration module and ledger;
- baseline empty creation;
- audited existing-database adoption;
- checksum/repeat/interruption behavior;
- test database integration.

**Done when:**

- empty and legacy fixtures reach the same required schema fingerprint;
- repeat invocation is a no-op;
- incompatible or modified applied migrations fail loudly;
- current public behavior remains compatible.

### R4 — Strict startup and SQLite enforcement

**Goal:** Prevent partial healthy startup and enable enforceable integrity.

**Scope:**

- required/optional initialization registry;
- removal of broad required-init suppression;
- `foreign_keys=ON`;
- orphan and `foreign_key_check` preflight;
- schema/startup health reporting.

**Done when:**

- required subsystem failure prevents healthy startup;
- optional failure is visible as degraded;
- every application connection enables foreign keys;
- existing fixtures pass or produce an explicit repair blocker.

### R5 — Recovery bundle integration

**Goal:** Integrate and harden the current backup/restore work under a stable
bundle contract.

**Scope:**

- review checkpointed backup code and tests;
- versioned manifest and complete durable-artifact classification;
- isolated local integration backend;
- encrypted off-device operator path;
- key recovery documentation;
- backup freshness/verification health.

**Done when:**

- snapshot consistency, manifest checks, tamper detection, missing key, and
  restore isolation tests pass;
- backup success alone is not reported as verified recovery;
- secrets never enter logs, Git, ordinary manifests, or handoffs.

### R6 — Application-aware restore and failure injection

**Goal:** Prove Crowley can resume from restored state.

**Scope:**

- restore migrations and startup against an isolated copy;
- bounded bus/health, ticket, Spark, and cognitive-context smoke;
- corrupt backup, interrupted migration, missing key, partial initialization,
  concurrent startup, and stale-lock tests;
- clean-machine-equivalent acceptance script.

**Done when:**

- restore drill reaches healthy required subsystem state;
- live state remains unchanged;
- every injected failure produces a truthful, recoverable result.

### R7 — Recovery lock and ladder reconciliation

**Goal:** Record verified recovery truth and unblock V4.4 planning.

**Scope:**

- recovery lock document with exact evidence;
- architecture/project-state/roadmap maintenance;
- historical incident and artifact classification;
- confirmation of the previously recorded V4.3.3 #491–#495 supersession;
- V4.4 plan reconciliation.

**Done when:**

- documentation describes only verified behavior;
- old tickets are superseded, not rewritten as if never approved;
- no historical database counts are represented as current;
- V4.4 is unblocked only after recovery acceptance passes.

## 11. Verification matrix

| Scenario | Required result |
|---|---|
| Empty database | Ordered schema, documented seed, healthy required subsystems |
| Compatible existing database | Snapshot, audited adoption, preserved rows |
| Unknown/incompatible schema | Startup blocked with actionable report |
| Repeated migration | No-op with unchanged checksum/state |
| Applied migration checksum changed | Startup blocked |
| Failure during migration | No false success; last committed state recoverable |
| Required subsystem setup fails | Startup unhealthy/fails |
| Optional embedding setup fails | Healthy core with explicit degradation |
| Orphaned reference exists | Adoption blocked or explicit repair required |
| Backup tampered | Verification fails |
| Encryption key missing | Restore fails clearly without data destruction |
| Restore drill | Isolated restore, migrate, start, smoke, report |
| Current live DB | Never overwritten by automated drill |
| Concurrent startup | One migration owner; bounded loser behavior |

Focused tests should be followed by full unit discovery, preflight, and bounded
runtime/API smoke once the environment is functional.

## 12. Compatibility implications

V4.3.3R must preserve:

- existing `crowley.setup_db()` callers through a compatibility wrapper;
- `crowley.connect_db()` public behavior except enforced integrity pragmas;
- current API and Actions response shapes unless an additive health field is
  approved;
- current ticket, handoff, Spark, memory, audit, and observability data;
- isolated test DB behavior;
- `crowley.py` as a thin compatibility facade.

Potentially affected areas that require contract tests:

- `crowley.py`, `crowley_core.py`, and subsystem setup helpers;
- application startup;
- tests using temporary databases;
- scripts that open SQLite directly instead of `connect_db()`;
- backup/restore tooling;
- health, preflight, and agent sync;
- Spark inserts once foreign keys are enforced.

---

## 13. Rollback and recovery

- Create and verify a pre-migration snapshot before adopting a real database.
- Never automate replacement of the live database.
- A failed migration is repaired with a new migration; an applied migration is
  not edited in place.
- Restoration targets a new path and requires operator-controlled promotion to
  live state.
- Every schema-changing handoff records the pre-change backup identity,
  migration IDs, verification, and recovery path.
- If the current database fails integrity or schema adoption, stop. Do not
  initialize over it or silently fall back to a new empty file.
