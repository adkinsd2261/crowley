# Crowley V3.6 — Memory Backend Plan

**Status:** Approved — V3.6.0 + Phases 1–4 shipped (2026-07-01)  
**Last updated:** 2026-07-01
**Baseline:** V3.5 (Chat UI)  
**Theme:** Hard-wired memory infrastructure — episodic capture, semantic retrieval, consolidation

---

## 1. Current memory architecture audit

### 1.1 Storage layers (as implemented)

| Layer | Table | Role | Indexed? | Project-scoped? |
|-------|-------|------|----------|-----------------|
| Raw log | `messages` | Every user/assistant turn | id, timestamp | No |
| Episodic | `memories` | Sparks + `/remember` pins | id only | No |
| Structured truth | `project_state` | Current phase, focus, risk, next action | project_id | Yes |
| Durable facts | `decisions` | Append-only decision log | project_id | Yes |
| Open work | `open_loops` | Unresolved items | project_id | Yes |
| Tasks | `tasks` | Todo list | status | Optional `project` text |
| Projects | `projects` | Active project metadata | status | — |

**Principle alignment (partial):**

- Messages are raw logs — **yes**
- Sparks are episodic memory — **yes, but underspecified** (`type` overloaded, `importance` used as tier)
- World model is current truth — **yes**, injected wholesale via `get_active_world_context()`
- Decisions are durable facts — **yes**, but **not参与 retrieval**; only surfaced in world/diagnostics panels
- Vector search — **no** (`chromadb`, `sentence-transformers` in `requirements.txt`, zero imports)
- Consolidation — **no** (no dedup, merge, stale handling, or daily rollups)

### 1.2 Write pipelines

| Trigger | Function | Output | Filters |
|---------|----------|--------|---------|
| User message saved | `save_message` → `should_create_implicit_spark` | `memories` row, `type='spark'`, importance=1 | Keywords, length, greetings, shell |
| After assistant reply | `maybe_create_spark` → `create_spark` | `memories` row, importance≥2 | ≥4 msgs since last summary spark, signal check |
| Manual CLI | `/remember type \| importance \| content` | `memories` row, arbitrary type | Importance 1–5 |
| Extraction (V3.2) | `maybe_extract_state` | `decisions`, `open_loops`, `project_state` | Confidence ≥0.85, dedupe 24h |

**Gaps:**

- No memory created from assistant-only insights (by design in V3.2)
- Summary sparks and trim sparks can overlap semantically
- No `message_id` link on memories — hard to trace provenance
- No embedding on write

### 1.3 Retrieval (updated — V3.6 shipped)

`build_prompt(user_message)` composes:

1. Personality + anti-hallucination rules
2. Full active world context (state + recent decisions + open loops)
3. Top `MEMORY_LIMIT` (8) from `retrieve_memories()` — **hybrid semantic + keyword**
4. Open tasks (top 5)
5. Last `CHAT_CONTEXT_LIMIT` (8) chat messages, 600-char cap each (V3.6.0)
6. Current user message

`retrieve_memories()` scores: semantic cosine, keyword overlap, recency, importance, type match, project match, pinned bonus. Modes: `vector+keyword` or `keyword-only fallback`.

`search_memories()` bag-of-words retained for legacy/debug only.

**Remaining gaps:**

- `/api/sparks` reads legacy `memories`, not all `memory_items` summaries
- Consolidation (Phase 4) shipped in V3.7.3

### 1.4 UI / API surface

- Web UI: messages, world, tasks, loops, decisions, summary sparks (legacy)
- V3.7 memory bus: `GET /api/context`, `GET /api/retrieve`, `POST /api/ingest`
- CLI: `/debug retrieve`, `/debug memory-items`, `/debug memories`, `/debug sparks`
- No in-browser "retrieved for this turn" panel yet (Phase 5 partial)

### 1.5 Dependencies

| Package | Status |
|---------|--------|
| `sentence-transformers` | ✅ Used for local embeddings |
| `sqlite-vec` | ✅ Used when SQLite extensions load |
| `chromadb` | ❌ Listed, never imported |
| `fastapi` / `uvicorn` | ✅ Web transport |

## 2. Proposed V3.6 memory architecture

```
                    ┌─────────────────────────────────────┐
                    │           build_prompt()            │
                    │  hybrid retrieve → rank → inject    │
                    └─────────────────┬───────────────────┘
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        ▼                             ▼                             ▼
 ┌──────────────┐            ┌──────────────┐            ┌──────────────┐
 │ project_state│            │ memory_items │            │ decisions    │
 │ (truth)      │            │ (episodic)   │            │ loops, tasks │
 └──────────────┘            └──────┬───────┘            └──────────────┘
                                    │
                            ┌───────▼────────┐
                            │ memory_vectors │
                            │ (sqlite-vec)   │
                            └────────────────┘

messages (raw) ──► classify ──► create memory_item ──► embed ──► index
                      │
                      └──► consolidate (session / daily / dedupe)
```

**Design tenets for V3.6:**

1. **SQLite remains source of truth** — one `crowley.db`, WAL, existing thread patterns
2. **memory_items replaces sparks conceptually** — migrate `memories` rows, deprecate table later
3. **Hybrid retrieval is default** — vector + keyword + metadata; never vector-only
4. **World model wins conflicts** — retrieval augments, does not override truth tables
5. **Passive capture** — no "remember this?" prompts for normal flow
6. **Inspectable** — debug/dry-run for retrieval and consolidation (matches extraction pattern)

**Optional V3.6.1:** Chat context window — **shipped as V3.6.0** (last 8 messages in `build_prompt`).

## 3. Recommended vector database choice

### Recommendation: **sqlite-vec** (primary)

| Criterion | sqlite-vec | ChromaDB |
|-----------|------------|----------|
| Single-file local-first | ✅ Same `crowley.db` | ❌ Separate store (`chroma/`) |
| Aligns with SQLite-as-truth | ✅ | ❌ Sync/duplication risk |
| Crowley scale (personal, <100k items) | ✅ Brute-force KNN sufficient | ✅ Overkill |
| Existing patterns | ✅ `connect_db()`, WAL | ❌ New client lifecycle |
| Backup/portability | ✅ Copy one file | ❌ Two systems |
| Maturity | ⚠️ Pre-v1, alpha | ✅ Stable |
| macOS Python | ⚠️ Needs extension-capable SQLite | ✅ Usually works |
| Dep already in requirements | ❌ Add `sqlite-vec` | ✅ Listed but unused |

**Decision:** Use **sqlite-vec** with `vec0` virtual table keyed to `memory_items.id`. Keep retrieval logic in `crowley.py`; no Chroma persistence.

**Fallback strategy:**

1. If `sqlite_vec.load()` fails at startup → log warning, run in **keyword-only mode** (current behavior)
2. Document Homebrew Python requirement on macOS if system SQLite blocks extensions
3. Do **not** implement Chroma dual-write in V3.6 — revisit only if sqlite-vec blocks target platforms

## 4. Schema additions

### 4.1 New table: `memory_items`

```sql
CREATE TABLE memory_items (
    id INTEGER PRIMARY KEY,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    project_id INTEGER REFERENCES projects(id),
    memory_type TEXT NOT NULL,
    content TEXT NOT NULL,
    summary TEXT,
    importance INTEGER NOT NULL DEFAULT 2,
    source TEXT NOT NULL,
    message_id INTEGER REFERENCES messages(id),
    decision_id INTEGER REFERENCES decisions(id),
    pinned INTEGER NOT NULL DEFAULT 0,
    status TEXT NOT NULL DEFAULT 'active',
    merged_into_id INTEGER REFERENCES memory_items(id),
    access_count INTEGER NOT NULL DEFAULT 0,
    last_accessed_at TEXT,
    embed_model TEXT,
    embed_dim INTEGER
);

CREATE INDEX idx_memory_items_status ON memory_items(status);
CREATE INDEX idx_memory_items_project ON memory_items(project_id);
CREATE INDEX idx_memory_items_type ON memory_items(memory_type);
CREATE INDEX idx_memory_items_created ON memory_items(created_at);
```

**memory_type enum:** `event`, `decision`, `preference`, `constraint`, `bug`, `qa_result`, `lesson`, `project_update`, `summary`

**source enum:** `implicit`, `session_summary`, `daily_summary`, `manual`, `consolidation`, `extraction_mirror`

**status enum:** `active`, `merged`, `stale`, `archived`

### 4.2 Vector index (sqlite-vec)

```sql
-- Created at runtime after sqlite_vec.load()
CREATE VIRTUAL TABLE memory_vec USING vec0(
    memory_id INTEGER PRIMARY KEY,
    embedding float[384]
);
```

Dimension fixed per `EMBED_DIM` constant; must match active embedding model.

### 4.3 Consolidation audit

```sql
CREATE TABLE memory_consolidation_runs (
    id INTEGER PRIMARY KEY,
    run_at TEXT NOT NULL,
    run_type TEXT NOT NULL,
    items_in INTEGER,
    items_out INTEGER,
    notes TEXT
);
```

### 4.4 Migration from `memories`

- One-time `migrate_memories_to_items()` on `setup_db()`:
  - `type='spark'`, importance=1 → `memory_type='event'`, `source='implicit'`
  - `type='spark'`, importance≥2 → `memory_type='summary'`, `source='session_summary'`
  - Other types → same `memory_type` as `type`, `source='manual'`, `pinned=1` if importance≥4
- Keep `memories` table read-only for one release; remove in V3.7
- Backfill embeddings in background job (batch)

**Why new table vs extend `memories`:** Current schema lacks `project_id`, `message_id`, `status`, `pinned`, provenance, and overloads `type`+'importance'. ALTER would be fragile; clean table matches V3.6 "infrastructure release" scope.

## 5. Embedding strategy

### 5.1 Provider resolution

```python
MEMORY_EMBED_PROVIDER = "auto"  # auto | local | openai | off
EMBED_MODEL_LOCAL = "all-MiniLM-L6-v2"   # 384 dim
EMBED_MODEL_OPENAI = "text-embedding-3-small"  # 1536 dim — use only if configured
EMBED_DIM = 384  # fixed per install; re-embed all if model changes
```

| Mode | When | Model |
|------|------|-------|
| `local` | Default | sentence-transformers `all-MiniLM-L6-v2` |
| `openai` | `OPENAI_API_KEY` + provider openai/auto | `text-embedding-3-small` with `dimensions=384` |
| `off` | User opt-out / load failure | Skip vector index; keyword-only |

### 5.2 When to embed

- On every new `memory_items` insert (sync in background thread, same pattern as sparks)
- On consolidation merge (re-embed merged summary)
- Migration backfill (batched, rate-limited)

### 5.3 Caching

- Store `embed_model`, `embed_dim` on row for invalidation detection
- If model changes → flag `needs_reembed` or run migration job

### 5.4 Fallback chain

1. Try local embed (lazy-load model on first use)
2. If local fails and OpenAI key → OpenAI embed
3. If all fail → insert memory_item without vector; keyword retrieval still works

**Do not** embed raw `messages` table in V3.6 — only curated `memory_items`.

## 6. Retrieval algorithm

### 6.1 Candidate generation (hybrid)

```
candidates = union(
    vector_search(query_embed, k=20),
    keyword_search(query, k=20),
    pinned_items(project_id, k=5),
    recent_summaries(project_id, k=3)
)
```

### 6.2 Scoring (weighted linear)

```python
score = (
    W_SEM   * cosine_similarity(query, item)      # 0.45
  + W_KW    * bow_score(query, item.content)      # 0.20
  + W_REC   * recency_decay(item.created_at)        # 0.15  # half-life ~30 days
  + W_IMP   * normalize(item.importance, 1, 5)    # 0.10
  + W_TYPE  * type_match(query, item.memory_type) # 0.05
  + W_PROJ  * (1.0 if item.project_id == active)    # 0.05
)
```

Tune weights via constants; expose in `/debug retrieve <query>`.

### 6.3 Type-aware boosts (examples)

| Query signal | Boost types |
|--------------|-------------|
| "bug", "broken", "error" | `bug`, `qa_result` |
| "decided", "approved" | `decision` (+ pull from `decisions` table directly) |
| "prefer", "always", "never" | `preference`, `constraint` |
| "we shipped", "released" | `project_update`, `event` |

### 6.4 Conflict resolution at inject time

Priority (high → low):

1. `project_state` fields — authoritative for phase, focus, risk, next_action
2. `decisions` table (recent, same project) — beats episodic paraphrase
3. `pinned` memory_items (`pinned=1` or manual `/remember`)
4. Active memory_items by score
5. Stale/merged items — excluded unless `status='active'`

**Rule:** If a memory_item contradicts `project_state.focus`, inject memory with lower precedence label:  
`(historical note)` vs state labeled `(current)`.

### 6.5 Prompt injection format

Replace flat `Relevant memories:` block with structured sections:

```
Current project state: …
Recent decisions: …
Retrieved memory (semantic):
- [preference|4] User prefers local-first SQLite …
- [lesson|3] Trim sparks need MAX_TRIM_LEN …
Pinned:
- …
```

Cap total tokens ~2–3k chars (existing `MEMORY_LINE_MAX` pattern).

## 7. Memory creation pipeline

```
save_message(user)
    │
    ├─► messages row (always)
    │
    └─► classify_user_message(content)
            │
            ├─ skip (noise filters — reuse should_create_implicit_spark logic)
            │
            └─ create_memory_item()
                    ├─ memory_type from classifier
                    ├─ project_id = active project
                    ├─ message_id = user message id
                    ├─ source = implicit | session_summary | …
                    └─ queue embed + index

chat_turn completes
    │
    ├─► maybe_create_session_summary()  # replaces maybe_create_spark
    │
    └─► maybe_extract_state()         # unchanged; decisions stay in decisions table
```

### 7.1 Classification — what becomes a memory item?

| Signal | memory_type | importance | Notes |
|--------|-------------|------------|-------|
| Architectural choice stated | `decision` or mirror to `decisions` via extraction | 3–4 | Prefer extraction for project decisions |
| User preference | `preference` | 3–4 | "I prefer X", "always use Y" |
| Hard constraint | `constraint` | 4–5 | "Never commit secrets", "no schema changes" |
| Bug / failure report | `bug` | 3 | |
| QA outcome | `qa_result` | 3 | "QA passed", "test failed because…" |
| Lesson learned | `lesson` | 3–4 | Retrospective insights |
| Project milestone | `project_update` | 2–3 | Shipped, phase complete |
| General episodic | `event` | 1–2 | Trim-level capture |
| Batch summary | `summary` | 2 | Session/daily consolidation |

**Phase 1 classifier:** Rule-based (extend `_SIGNAL_KEYWORDS` + regex patterns).  
**Phase 2 (optional):** Small `call_model(quiet=True)` JSON classify for ambiguous messages — same pattern as extraction.

### 7.2 Manual `/remember`

Maps to `memory_items` with `pinned=1`, `source='manual'`, user-chosen type and importance. Always included in retrieval candidate set when loosely relevant.

## 8. Consolidation pipeline

### 8.1 Session summary (replaces summary sparks)

- Trigger: ≥`SESSION_SUMMARY_MESSAGE_THRESHOLD` (4) messages since last `source='session_summary'`
- Input: messages since last summary
- Output: one `memory_type='summary'` item; mark contributing trim events as `merged` if superseded
- Run: background thread + lock (reuse `_spark_lock` pattern)

### 8.2 Daily summary (opt-in)

- Trigger: `MEMORY_DAILY_SUMMARY=1` or local cron calling `crowley.py --consolidate daily`
- Input: all `memory_items` + messages from last 24h
- Output: single `summary` item with `importance=3`

### 8.3 Duplicate merging

- Nightly or on-write debounce: find pairs same `project_id`, `cosine_sim ≥ 0.92`, same or compatible `memory_type`
- Keep newer; set older `status='merged'`, `merged_into_id=newer.id`
- Optional: LLM one-liner merge into `summary` field on newer row

### 8.4 Stale handling

- Items with `importance ≤ 2`, `access_count=0`, age > 90 days → `status='stale'`
- Stale excluded from default retrieval; recoverable via `/debug memories --stale`
- **Never auto-delete** (aligns with project safety principles)

## 9. Risks and mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| sqlite-vec pre-v1 / macOS extension issues | No vector search | Graceful degrade to keyword-only; document Python/SQLite setup |
| sentence-transformers + torch size | Slow cold start, large venv | Lazy load; optional `MEMORY_EMBED_PROVIDER=openai`; document minimal install |
| False memories from bad summaries | Wrong retrieval | Conservative filters; consolidation merge review via debug; pin corrections |
| Embedding API cost | $$ on OpenAI | Default local; batch embed; cache forever |
| SQLite lock contention | Skipped writes | Fresh conn per background job (existing pattern); embed queue |
| Migration data loss | Broken recall | Non-destructive migrate; keep `memories` table one release |
| Duplicate decisions (extraction + memory) | Redundant prompt | `extraction_mirror` source dedupes against `decisions` table |
| Over-retrieval noise | Prompt bloat | Hard cap items; raise importance threshold for implicit types |
| Model without chat history | Apparent amnesia mid-thread | Document; consider V3.6.1 sliding window separately |

## 10. Phase-by-phase implementation plan

### Phase 1 — Foundation (schema + embed + index) ✅ SHIPPED

- Add `memory_items`, migration from `memories`
- `sqlite_vec` load + `memory_vec` virtual table (when extensions available)
- `embedding_blob` fallback when vec extension unavailable
- `embed_text()`, `index_memory_embedding()`, `backfill_memory_item_embeddings()`
- **Not shipped:** dual-write from `save_memory`, hybrid retrieval

**Exit criteria met:** Schema inspectable; migrated items embeddable; retrieval unchanged.

### Phase 2 — Hybrid retrieval ✅ SHIPPED

- `retrieve_memories()` with weighted scoring and `score_breakdown`
- Wired into `build_prompt()` as `Relevant long-term memory`
- `/debug retrieve <query>` — mode + score breakdown
- Vector via sqlite-vec or `embedding_blob` fallback; keyword-only when no embeddings

**Exit:** Semantic + keyword retrieval live; graceful degrade; world model + chat context preserved.

### Phase 3 — Dual-write creation pipeline ✅ SHIPPED

- `save_memory_item()` with dedupe, embedding, and vector index
- `save_memory()` dual-writes to `memory_items` for /remember, trim sparks, summary sparks
- `/debug memory-items`

**Exit:** New memories discoverable via `retrieve_memories()` immediately after creation.

### Phase 4 — Consolidation ✅ SHIPPED (V3.7.3)

- Session summary merge logic (`merge_implicit_since_session_summary` on spark create)
- Duplicate detection job (cosine ≥ 0.92)
- Stale marking job (90d, importance ≤ 2, access_count = 0)
- Optional daily summary (`MEMORY_DAILY_SUMMARY=1`, `--consolidate daily`)
- `memory_consolidation_runs` audit table
- CLI `/debug consolidate`, `python crowley.py --consolidate`, `POST /api/consolidate`

**Exit:** Memory count grows sublinearly with chat volume.

### Phase 5 — UI + API (partial)

- ✅ `GET /api/retrieve` — shipped in V3.7 Phase 2
- ✅ `GET /api/context` — includes relevant memories — V3.7 Phase 1
- ⏳ Intelligence drawer **Memory** tab — not built
- ⏳ `GET /api/memories` — not built

### Phase 6 — Version ship

- Bump `CROWLEY_VERSION` → `3.6`
- `VERSIONS.md` entry
- Deprecation notice on `memories` table
- QA sign-off

## 12. What NOT to build in V3.6

| Out of scope | Reason |
|--------------|--------|
| ChromaDB production integration | sqlite-vec chosen; avoid dual store |
| Embedding every `messages` row | Cost, noise; curated items only |
| Auto-delete memories | Safety principle |
| Multi-project memory routing UI | Schema supports `project_id`; runtime still single active project |
| User-facing memory edit/delete UI | Inspection/debug only; CLI pin remains |
| LLM-generated memory without filters | Rules-first; model classify is Phase 2 optional |
| Chat history window in `build_prompt` | Shipped V3.6.0 |
| Cross-device sync | Local-first |
| Real-time memory graph visualization | Premium UI distraction |
| Replacing `decisions` table with memories | Decisions stay authoritative |
| Rewriting extraction | Touch only for optional `extraction_mirror` dedup |
| Agent tool-use / external collectors | Future roadmap |
