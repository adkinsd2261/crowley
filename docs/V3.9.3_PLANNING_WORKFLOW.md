## 1. Purpose

Turn Mr. Go + Codex planning into a repeatable pipeline: brainstorm when useful, mint **Cursor-ready tickets** when work is concrete, and let **Crowley** hold the shared truth.

Principle (same as Pre-V4 plan):

> Crowley should feel natural in conversation, but auditable on demand.

---

## 2. Roles

| Actor | Role | Does | Does not |
|-------|------|------|----------|
| **Mr. Go** | Intent | Sets direction, priorities, approvals, and "done means…" | Mint tickets or ship code |
| **Codex** | Architect | Plans, decomposes work, writes specs, mints tickets, posts architect handoffs | Build implementation or speak as Crowley |
| **Cursor** | Builder | Implements tickets, runs tests, posts builder handoffs, closes tickets | Architect in Codex's lane unless Mr. Go asks for planning here |
| **Crowley** | Hub / OS | Stores memory, tickets, agent activity, canon, and world state; answers in the browser | Replace Codex planning or Cursor building |

**Crowley is the only hub.** Codex and Cursor do not message each other directly. Each agent reads the other only through Crowley (`events_from_other_agents` after sync).

## 3. When to brainstorm vs mint tickets

### Stay in brainstorming (no ticket yet)

- Direction is still open ("should we do X or Y?")
- Scope is fuzzy or depends on a spike
- Mr. Go is exploring trade-offs, not assigning build work
- Output is a decision or ADR, not a shippable slice

**Codex action:** `--after` or `--note` with summary, decision, and next action. Update planning docs if the decision is durable.

### Mint tickets

- Work is concrete enough for Cursor to implement without guessing
- Acceptance criteria can be written as checkable outcomes
- Priority and assignee are clear (`cursor` for build work)
- The slice fits one focused PR or one builder session

**Codex action:** `--create-ticket` or `--create-tickets` after Mr. Go approves the plan (or when the plan is already approved in session).

### Rule of thumb

If Cursor would need to ask "what exactly should I build?" — keep planning. If Cursor can run `--before`, read the ticket, implement, test, and hand off — mint the ticket.

## 4. Planning packets and tickets

| Artifact | Owner | When |
|----------|-------|------|
| **Planning packet** | Codex | Multi-ticket initiative **before** minting |
| **Ticket** | Codex mints → Cursor claims | Single buildable unit of work **after approval** |
| **Handoff** | Codex or Cursor | After a meaningful planning or build block |
| **Memory / canon** | Crowley ingests | Durable truth from handoffs and operator runs |

A planning packet is **pre-ticket**. Tickets are **post-approval** and appear on the board for Cursor.

### Approval gate (required)

1. Codex drafts a planning packet from the template.
2. Mr. Go reviews objective, risks, non-goals, and ticket slices.
3. Set `approval.status` to `approved` in the packet (with `approved_by` / `approved_at`).
4. Only then run `--create-tickets` — **never mint while `approval.status` is `pending`**.

Cursor should not start implementation tickets until they exist on the board from an approved mint.

### Cancel versus edit

Use **edit** (`PATCH /api/tickets/{id}`) when the ticket is still valid work but scope, priority, assignee, or description needs to change.

Use **cancel** when the ticket should leave the open board without implying shipped work:

| Situation | Action |
|-----------|--------|
| Accidental early mint before approval | Cancel with reason referencing the approved replacement |
| Draft planning ticket superseded by a new slice list | Cancel with `superseded by #N` or initiative name |
| Duplicate or wrong ticket minted from a packet | Cancel the bad row; mint or keep the correct ticket |
| Work shipped under a different ticket | Cancel the stale row; mark the real ticket `done` |

Cancellation is **Codex or Mr. Go only** (Cursor marks builder tickets `done`, not `cancelled`). Always include a short reason — it is stored on the `cancelled` ticket event.

```bash
./venv/bin/python3 scripts/codex_sync.py --cancel-ticket 4 \
  --comment "Superseded by tickets #9-#23 from approved Pre-V4 plan"
```

Cancelled tickets remain in history (`GET /api/tickets?status=cancelled`, ticket detail events) but are excluded from open summaries and agent assigned work.

### Packet fields

| Field | Purpose |
|-------|---------|
| `objective` | One-line outcome for the initiative |
| `context` | Baseline, constraints, doc links |
| `decisions` | Boundaries already chosen |
| `non_goals` | Initiative-level exclusions |
| `risks` | Dependencies and watch items |
| `qa_expectations` | Regression bar for the initiative |
| `next_action` | First step after approval (usually mint command) |
| `approval` | Mr. Go sign-off metadata — must be `approved` before mint |
| `tickets` | Cursor-ready slices (see below); optional `parent_id` links child work to an initiative ticket |

### Copying ticket slices to `--create-tickets`

The `tickets` array in a planning packet uses the same core fields as mint JSON:

- `title`, `assignee`, `priority`, `description`, `acceptance` (required for mint)
- `non_goals`, `qa_expectation` (per-slice — fold into `description` when minting if needed)

To mint from a packet file that includes planning metadata:

```bash
# 1. Copy the tickets array into a mint-only file, e.g. tickets/my_initiative.json:
#    { "tickets": [ ... slices from approved packet ... ] }
# 2. After approval:
./venv/bin/python3 scripts/codex_sync.py --create-tickets tickets/my_initiative.json
```

`--create-tickets` validates every slice before minting. Missing title, assignee, priority, description, or acceptance criteria fails with a full error list and **creates zero tickets**.

Or mint the curated release list:

```bash
./venv/bin/python3 scripts/codex_sync.py --create-tickets tickets/pre_v4_release_plan.json
```

## 5. Cursor-ready tickets

A ticket is **Cursor-ready** when Cursor can implement it without reopening architecture.

Each ticket should include:

| Field | Required | Notes |
|-------|----------|-------|
| **Title** | Yes | One clear outcome |
| **Description / scope** | Yes | What to build; files or surfaces if known |
| **Acceptance criteria** | Yes | Checkable list — tests, API behavior, docs updated |
| **QA expectation** | Yes | e.g. "focused tests pass", "full suite N/N", manual step |
| **Non-goals** | Yes (can be "none") | What is explicitly out of scope |
| **Assignee** | Yes | Usually `cursor` for implementation |
| **Priority** | Yes | P1–P4 on the board |

**Good acceptance example:**

- `GET /api/memory/hygiene` returns grouped stale/noisy/duplicate/conflict candidates
- Dry-run makes no DB writes
- `tests.test_memory_hygiene` passes

**Weak acceptance (avoid):**

- "Make memory better"
- "Improve UX"

Codex mint example:

```bash
./venv/bin/python3 scripts/codex_sync.py --create-ticket \
  --title "V3.9.3 Planning Workflow: document planning roles" \
  --assignee cursor --priority 1 \
  --description "Create docs/V3.9.3_PLANNING_WORKFLOW.md…" \
  --acceptance "Doc explains roles; defines Cursor-ready tickets; WHERE_WE_ARE links here"
```

## 6. Agent rituals (summary)

### Codex

```bash
./venv/bin/python3 scripts/codex_sync.py --before
# plan, decide, mint tickets when ready
./venv/bin/python3 scripts/codex_sync.py --after \
  --summary "…" --next-action "…" --decision "…"
```

See [CODEX.md](../CODEX.md).

### Cursor

Hooks run `cursor_sync.py --before` on session start. After shipping:

```bash
./venv/bin/python3 scripts/cursor_sync.py --after --ticket <ID> \
  --summary "…" --next-action "…" --qa-result "tests OK"
```

See [CURSOR.md](../CURSOR.md).

### Mr. Go

- Talks to **Crowley** in the browser for system truth and status
- Sets intent with Codex for planning; does not need to relay plans to Cursor manually

---

## 7. What not to do

- Do **not** imply Codex and Cursor chat directly or share a private thread
- Do **not** mint tickets before scope and acceptance are clear
- Do **not** skip Crowley handoffs after planning or shipping — Mr. Go and the other agent rely on memory trail
- Do **not** treat hybrid memory retrieval as a substitute for tickets or filesystem docs ([MEMORY_HIERARCHY.md](./MEMORY_HIERARCHY.md))
