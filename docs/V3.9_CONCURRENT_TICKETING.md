# Crowley V3.9 — Concurrent Ticketing

**Status:** Shipped (2026-07-01)  
**Release:** `CROWLEY_VERSION = "3.9"`, `CROWLEY_RELEASE_LABEL = "Crowley V3.9 Concurrent Ticketing"`  
**Baseline:** V3.8.1 Agent Parity  
**Owner split:** Codex plans and mints tickets · Cursor implements tickets · Crowley holds truth

---

## 1. Purpose

V3.8 gave agents a **shared memory hub**. V3.9 gives them a **shared work board**.

Today, work is scattered across `tasks`, `open_loops`, and `docs/TICKETS.md`. Codex can describe work in handoffs; Cursor can read it — but nothing is **assignable, claimable, or closable** through the bus with stable IDs.

V3.9 introduces one **ticket system** that all models use concurrently through Crowley:

```
Mr. Go ──► Crowley (ticket store + chat + UI)
              ▲
         ticket ops + handoffs
              │
         ┌────┴────┐
      Codex       Cursor
    (creates)    (claims → ships → closes)
```

**Concurrent** means multiple tickets can be open; each agent sees the same board on sync; no agent messages another directly.

---

## 2. Problems solved

| Problem | V3.9 fix |
|---------|----------|
| Codex plan is prose-only | Structured tickets via API + `--create-tickets` |
| Cursor doesn't know what to pick up | `assignee=cursor`, `status=open`, ordered by priority |
| No link handoff ↔ work item | `ticket_events` + `--ticket` on sync scripts |
| `tasks` vs `open_loops` vs markdown | Unified `tickets` table; legacy tables kept, not removed |
| Crowley can't answer "what's blocked?" | Ticket block in `build_prompt()` + `/api/tickets` |

---

## 3. Design principles

1. **Crowley owns tickets** — SQLite source of truth; HTTP bus for agents.
2. **Hub only** — agents never assign each other; they read/write Crowley.
3. **Conservative writes** — append event log; no hard deletes; `cancelled` not delete.
4. **Handoff + ticket** — closing builder work requires both ingest and ticket transition (when `--ticket` given).
5. **Backward compatible** — existing `tasks` / `open_loops` / UI keep working; optional migration helper later.
6. **Engine in `crowley.py`** — `app.py` transport only (same as V3.7+).

## 4. Data model

### 4.1 `tickets` table

| Column | Type | Notes |
|--------|------|-------|
| `id` | INTEGER PK | Stable ID; display as `#42` or `TKT-42` |
| `project_id` | INTEGER FK | Active project |
| `title` | TEXT NOT NULL | One line |
| `description` | TEXT | Scope, files, acceptance (markdown ok) |
| `status` | TEXT NOT NULL | See §4.3 |
| `assignee` | TEXT NOT NULL | `codex` \| `cursor` \| `crowley` \| `mr_go` \| `unassigned` |
| `priority` | INTEGER NOT NULL | 1=highest (P1), 4=lowest (P4); default 2 |
| `parent_id` | INTEGER NULL | Epic → subtask |
| `blocked_by_ticket_id` | INTEGER NULL | Optional blocker ref |
| `source` | TEXT NOT NULL | Who created: `codex`, `cursor`, `mr_go`, `crowley`, `manual` |
| `created_at` | TEXT NOT NULL | ISO UTC |
| `updated_at` | TEXT NOT NULL | ISO UTC |
| `closed_at` | TEXT NULL | Set when `status=done` or `cancelled` |
| `linked_memory_id` | INTEGER NULL | Handoff that created or last updated ticket |

Indexes: `(project_id, status)`, `(assignee, status)`, `(parent_id)`.

### 4.2 `ticket_events` table (append-only)

| Column | Type | Notes |
|--------|------|-------|
| `id` | INTEGER PK | |
| `ticket_id` | INTEGER FK | |
| `event_type` | TEXT | `created`, `claimed`, `status_change`, `comment`, `handoff_linked`, `assignee_change`, `priority_change` |
| `actor` | TEXT | `codex`, `cursor`, `mr_go`, `crowley`, `system` |
| `payload` | TEXT | JSON blob (old/new status, comment text, memory_id, etc.) |
| `created_at` | TEXT | ISO UTC |

### 4.3 Status workflow

```
open ──► claimed ──► in_progress ──► done
  │                      │
  └──────► blocked ◄─────┘
  │
  └──► cancelled
```

| Status | Meaning |
|--------|---------|
| `open` | Ready; unclaimed or waiting |
| `claimed` | Assignee acknowledged (optional step; Cursor may skip to `in_progress`) |
| `in_progress` | Active work |
| `blocked` | Cannot proceed; `blocked_by_ticket_id` or comment required |
| `done` | Shipped; requires builder handoff when assignee was `cursor` |
| `cancelled` | Won't do; Codex or Mr. Go only |

**Rules:**

- Codex may create, reprioritize, cancel, unblock.
- Cursor may claim, move to `in_progress`, mark `done` (with handoff), mark `blocked`.
- Mr. Go may override anything via UI/API.

### 4.4 Relationship to legacy tables

| Legacy | V3.9 approach |
|--------|----------------|
| `tasks` | Keep; do not auto-sync. Optional `scripts/migrate_tasks_to_tickets.py` later |
| `open_loops` | Keep; extraction may still add loops. Tickets are the **agent work board** |
| `docs/TICKETS.md` | Becomes optional export / human mirror; not source of truth |

## 5. HTTP API (`127.0.0.1:8765`)

### GET `/api/tickets`

Query params:

| Param | Default | Description |
|-------|---------|-------------|
| `status` | all open statuses | Comma-separated or `all` |
| `assignee` | — | Filter by assignee |
| `priority` | — | Max priority (e.g. `2` = P1–P2) |
| `parent_id` | — | Subtasks of epic |
| `limit` | 50 | Cap |
| `offset` | 0 | Pagination |

Response: `{ tickets: [...], total, limit, offset }`.

### GET `/api/tickets/{id}`

Single ticket + last 20 `ticket_events`.

### POST `/api/tickets`

Create ticket (Codex, manual, UI).

```json
{
  "title": "Add tickets schema",
  "description": "…",
  "assignee": "cursor",
  "priority": 1,
  "parent_id": null,
  "source": "codex"
}
```

Returns `{ ticket, event }`.

### PATCH `/api/tickets/{id}`

Update status, assignee, priority, blocked_by, description.

```json
{
  "status": "in_progress",
  "actor": "cursor",
  "comment": "Starting schema migration"
}
```

Appends `ticket_events` row; updates `updated_at`.

### POST `/api/tickets/{id}/done`

Shortcut: `status=done`, `closed_at=now`, event `status_change`. Idempotent if already done.

### Bundle exposure

Add to `build_context_bundle()`, `build_agent_sync_bundle()`, `build_world_dashboard()`:

```json
"tickets": {
  "open": [...],
  "assigned_to_agent": [...],
  "blocked": [...],
  "recently_closed": [...]
}
```

`assigned_to_agent` filtered by requesting agent on `/api/agent/sync`.

## 6. Agent rituals

### Codex (architect)

**After planning session** — mint tickets from plan:

```bash
./venv/bin/python3 scripts/codex_sync.py --after \
  --summary "V3.9 plan approved; N builder tickets created" \
  --next-action "Cursor: start TKT-3901" \
  --create-tickets tickets/v3.9_builder.json
```

Or inline:

```bash
./venv/bin/python3 scripts/codex_sync.py --create-ticket \
  --title "Tickets schema + migrations" \
  --assignee cursor \
  --priority 1 \
  --description "Acceptance: …"
```

`--create-tickets` JSON file format:

```json
{
  "tickets": [
    {
      "title": "…",
      "description": "…",
      "assignee": "cursor",
      "priority": 1,
      "acceptance": "…"
    }
  ]
}
```

Codex does **not** mark builder tickets `done`.

### Cursor (builder)

**Before work:**

```bash
./venv/bin/python3 scripts/cursor_sync.py --before
```

Read `tickets.assigned_to_agent` + `open` P1 items.

**During work** — optional claim:

```bash
./venv/bin/python3 scripts/cursor_sync.py --claim-ticket 3901
```

**After shipping:**

```bash
./venv/bin/python3 scripts/cursor_sync.py --after \
  --ticket 3901 \
  --summary "TKT-3901: schema shipped" \
  --next-action "TKT-3902: HTTP routes" \
  --qa-result "N tests OK"
```

`--after --ticket ID` must:

1. Ingest handoff (existing path)
2. `PATCH` ticket → `done` if ingest verify succeeds
3. Append `handoff_linked` event with `memory_id`

### Crowley (chat)

Answers from **Tickets** block in `build_prompt()`:

- What's open for Cursor?
- What's blocked?
- What did Codex assign?

Same authority tier as **Agent activity** for operational questions.

## 8. `build_prompt()` ticket block (spec)

```
Tickets (authoritative work board — use for what is assigned, blocked, or in flight):

Open for Cursor (P1–P2):
- #3901 [in_progress] Tickets schema + engine — Codex/V3.9 plan
- #3902 [open] HTTP routes — blocked by #3901

Blocked:
- (none)

Recently closed:
- (none)
```

Precedence for work questions:

```
filesystem docs  >  tickets  >  agent_activity  >  project_state  >  canon  >  memory
```

Tickets beat hybrid memory for "what should Cursor build next?" but not for version history (filesystem).

## 11. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Schema drift without migration table | `CREATE IF NOT EXISTS` only; additive columns |
| Codex creates vague tickets | Require `description` + acceptance in `--create-tickets` validation |
| Cursor closes without shipping | `--ticket` only closes after ingest verify (same as V3.8.1 handoff verify) |
| Ticket / task confusion | Clear naming; tasks tab unchanged |
| Board overload in prompt | Cap at 10 open + 5 recent closed in prompt section |
