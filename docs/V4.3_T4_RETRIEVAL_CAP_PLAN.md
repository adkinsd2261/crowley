## Goal

Align cognitive depth limits so the **default medium** API/Actions profile returns **≤15 sparks total** (`core + supporting`), never silent overflow. Report `trace.truncated_count` when the ranked pool exceeds the applied cap. **Deep** may return more **only** with explicit `depth=deep`.

**Non-goals for T4:** V4.3 lock / acceptance test 2 (#362), chat/`build_prompt`, token budget packing (V4.4), scoring/lane/query-mode changes, tools-registry contract rewrites, legacy `/api/retrieve`, V4.2 ingest.

## Design principles

1. **Cap is orchestration-owned** — `build_cognitive_context` enforces total spark budget; `retrieve_sparks` keeps an explicit `limit=` (no silent reinterpret of mode).
2. **Medium hard total = 15** — matches packet decision + acceptance matrix.
3. **Light stays lean** — core-only, within the 8–15 band.
4. **Deep is opt-in** — higher totals only when caller passes `depth=deep` (not the default).
5. **No silent overflow** — if ranked candidates exceed the applied total, slice and set `truncated_count`.
6. **Stay in lane** — do not touch scoring profiles, lane inference, chat, or tools contract beyond existing params.

|-------|------|------------|----------|------------------|
| **light** | **8** | **0** | 5 | **8** |

- Light sits at the low end of the 8–15 band (core-only).

- Patterns remain separate (not counted in the spark total / acceptance `retrieved_count`).

## Truncation semantics

In `build_cognitive_context`:

1. Resolve `core_limit` / `support_limit` from depth + caller args (existing `min` logic).
2. `total_cap = core_limit + support_limit`.
3. Call `retrieve_sparks(..., limit=total_cap)` as today (fetch only what we will use).
4. To detect truncation honestly when the pool is larger than the cap:
   - **Preferred:** retrieve with `limit=total_cap + 1` (or a small probe), then if `len(ranked_raw) > total_cap`, set `truncated_count = len(ranked_raw) - total_cap` after slicing to `total_cap`, **or**
   - **Simpler / recommended:** always request `limit=total_cap`, and set `truncated_count` only when an explicit overflow signal exists.

**Recommended approach (clear + cheap + expansion-safe):**

```python
probe_limit = total_cap + 1
ranked_raw = retrieve_sparks(
    ...,
    limit=probe_limit,
    expand_seed_limit=total_cap,  # REQUIRED: overflow must not seed expansion
)
truncated_count = max(0, len(ranked_raw) - total_cap)
ranked = ranked_raw[:total_cap]
```

`retrieve_sparks` gains optional `expand_seed_limit` (default `None` → seed from `limit` as before). When set, graph expansion and access bumps use only the first `expand_seed_limit` ranked rows.

Then split:

```python
core = ranked[:core_limit]
supporting = ranked[core_limit : core_limit + support_limit]
```

Trace fields:

| Field | Meaning |
|-------|---------|
| `retrieved_count` | `len(ranked)` after cap (**≤ total_cap**) |
| `truncated_count` | extras beyond cap (`0` when no overflow) |
| `core_count` / `supporting_count` | post-split lengths |
| existing T1–T3 fields | unchanged (`query_mode`, `lane_source`, `score_profile`, …) |

Always include `truncated_count` (integer ≥ 0), not only when > 0 — easier for clients/tests.

**Cold-start `memory_fallback`:** remains additive under existing rules; **not** counted toward the 15-spark cap (those are legacy memory items, not sparks). Do not change fallback threshold in T4.
