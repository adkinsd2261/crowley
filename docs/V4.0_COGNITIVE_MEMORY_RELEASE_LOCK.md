# V4.0 Cognitive Memory Release Lock

**Status:** Shipped  
**Date:** 2026-07-08  
**Version constant:** `CROWLEY_VERSION = "4.0.0"`  
**Release label:** `Crowley V4.0 Cognitive Memory`  
**Ticket packet:** `tickets/v4.0_cognitive_memory.json` (#203-#226)

V4.0 makes Crowley's memory stack explicitly cognitive: raw receipts remain in
`memory_items`, but durable recall now flows through lane-scoped sparks, graph
links, patterns, deterministic context orchestration, security gates, and lineage
traces.

## Architecture

```
memory_items raw receipts
  -> sparks durable 300-char lane units
  -> spark_links graph reinforcement
  -> patterns cluster summaries
  -> /api/cognitive/context read-only context bundle
```

The old memory system is not removed. `memory_items`, `/api/ingest`,
`/api/context`, `/api/retrieve`, portable writeback, tickets, and ChatGPT Actions
continue to exist. V4 adds the `/api/cognitive/*` namespace and the `sparks`,
`spark_links`, `patterns`, and `spark_vec` tables.

## API Surfaces

| Surface | Role |
|---------|------|
| `POST /api/cognitive/ingest` | Synchronously saves a raw receipt, then extracts candidate sparks inline with `sync=1` or asynchronously by default |
| `GET /api/cognitive/context` | Returns core/supporting sparks, attached active patterns, confidence, depth, and trace |
| `POST /api/cognitive/maintenance` | Dry-run by default; transitions stale/rejected states without hard deletes |
| `POST /api/cognitive/sparks` | Manual seed path for validated spark candidates |
| `cognitive.context` Actions tool | Bearer-gated read access to the same deterministic context builder |

## Safeguards

- Spark content is capped at 300 chars and validated before persistence.
- Cognitive ingest body is capped at 32KB and rate-limited to 10/min per source.
- Spark extraction uses OpenAI only for JSON-array extraction; retrieval, ranking,
  lane selection, graph expansion, lifecycle, and exposure gates are deterministic
  code.
- `validate_spark()` rejects embedded instructions, prompt wrappers, secret-like
  patterns, raw `MEMORY_DATA` delimiter smuggling, and spark-shaped hallucinated
  structures while allowing ordinary technical prose.
- Cognitive context output sanitizes returned text: instruction-like phrases are
  neutralized, `sk-*` and `Bearer` secrets are redacted, and memory text is wrapped
  in idempotent `MEMORY_DATA` delimiters.
- Sensitive and high-sensitivity sparks are exposure-gated by lane; high
  sensitivity also requires non-light depth and score > 0.7.
- Lifecycle maintenance never hard-deletes sparks. Low-usage rows become `stale`
  or `rejected`; pinned sparks are exempt from transition but still use normal
  read-time confidence decay.
- Cognitive direct APIs write to the existing observability hash chain.

## Lineage

Spark creation records lineage in `lineage_json`, including `memory_item_id`,
`source_memory_item_id`, extraction or seed/writeback metadata, and
`dedup_action`. Merge evidence is preserved in `source_refs_json`. Cognitive
context trace exposes per-spark lineage metadata without exposing raw content
outside the sanitized context fields.

## Trust Boundaries

- `memory_items` are raw receipts and legacy memory rows.
- `sparks` are compact cognitive units with `trust_state`.
- `patterns` are active cluster summaries only; they do not auto-canonize and do
  not feed back into spark extraction.
- Canon remains manual and still ranks below filesystem docs, tickets, agent
  activity, and live project state for factual authority.
